# git blame me

*A build log by Miguel Buddle.*

`git blame` is the command that shows who wrote each line of code. In this log, the answer is usually me. Kind of.

## What this is

I've worked close to technology my whole career, in post-sales, services, delivery and implementation, and I've spent a lot of that time next to some extremely good developers. I was never able to build software on my own. Now I can, with Claude and Claude Code. The hard part isn't building fast. It's building it right.

On March 29, 2026 I started building an AI system as a side project with a friend who is a forensic psychiatrist. It helps an expert review hospital records after a death or serious harm. It asks what should be in the record and isn't, and whether the response came in time. The expert keeps the final judgment.

Work like that can't be sloppy. This log tells how it got built, in order, one chapter a week, from the first commit to now.

It's also a record of learning. I've used Claude and Claude Code not only to build, but to learn how software should be built and why. Each chapter names the models and tools I used, why I chose them, and what I had to learn along the way.

## How each entry works

Every entry answers the same seven questions:

1. What was I trying to do?
2. What did I do?
3. What went wrong?
4. What did I change?
5. What would I tell another executive building with AI?
6. Under the hood: which tools and models, why those, what I researched first, and what I learned.
7. The check I added: what now stops the same mistake from happening again?

Every entry names at least one mistake. Some are mine. Some are the AI's. A few are both. Where a fix came from having the AI research how something should be built before building it, the entry says so.

## Ground rules

- Everything in this log was built and tested on invented cases. No real patient records went into any of it.
- The product stays unnamed.
- How the system reaches its conclusions may go into a research paper, so it stays out of here. So do accuracy results.
- Engineering facts are fair game: tools, models, costs, setup, and what broke.
- Security problems appear only after they were fixed.
